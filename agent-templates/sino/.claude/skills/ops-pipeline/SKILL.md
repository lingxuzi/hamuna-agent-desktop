# ops-pipeline — 运营主控

这个 skill 是运营循环的调度台，不是另一份业务细则。细则在各子 skill 里；这里决定**现在做哪一步、交给谁、什么条件才能往下走、什么情况必须停**。

台账纪律见 `05-OPS.md`：`ops/state.json` 只通过 `hamuna ops` 读写，绝不直接编辑。

## 循环总览

```text
intake → direction/benchmark → topic → produce → schedule → publish → review
   ^                                                                      |
   |                                                                      |
   +-------------------------- rules / clues / gaps -----------------------+
```

不是每次都从 intake 开头。大多数时候是从当前台账状态进入循环中段：有到点要发的就发，有 ready 没排的就排，有选题待做的就做，有数据待复盘的就复盘。

## 先看现场，再决定动作

每次接手先拿事实，不凭印象：

```bash
hamuna ops list --json          # 全量，一次拿齐
hamuna ops list asset --json    # 只看素材
hamuna ops list topic --json    # 只看选题
```

> **kind 必须用单数**：`direction / topic / asset / review / rule / account / clue / benchmark`。
> 写复数（`assets`）不会报错 —— `ops` 的动词只有 `list / add / update / remove`，认不出的
> 词静默兜底成「读全量」，你会拿到全部记录并误以为是单个 kind 的结果。`stats`、`get`、
> `due` 同理，全都不存在。要看某条细节自己从 `--json` 里挑。

只拉当前决策需要的范围。

扫完后按下面的优先级判断当前动作：

| 优先级 | 信号 | 动作 | 交给 |
|---|---|---|---|
| P0 | 有 `ready` 且 `scheduledAt` 已过，且当前会话有浏览器面板、用户明确要求发布 | 走发布 | `ops-publish` |
| P0 | 有 `ready` 且 `scheduledAt` 已过，但没有面板 / 用户没点头 | **只提醒，不发布** | 向用户报告，等确认 |
| P1 | 有已投放素材缺复盘（投放后有数据窗口） | 补复盘 | `ops-review` |
| P2 | 有 `planned` 选题或用户点名要做的素材 | 做素材 | `ops-produce` |
| P3 | 有 `ready` 但没排期 | 排期 | `ops-schedule` |
| P4 | 有方向但缺可执行选题；或热点有更新但没出简报 | 选题 / 扫热点 | `ops-topic` / `ops-signal` |
| P5 | 冷启动/方向缺失/方向过期 | 定方向、找对标 | `ops-direction` / `ops-benchmark` |
| P6 | `ops/materials/` 有文件没登记 / 有登记没描述 | 物料入库 | `ops-intake` |

> **P2 的状态是 `planned`**，不是 `approved/doing` —— 选题状态只有
> `idea / planned / produced / dropped` 四个值。
>
> **P4 两条腿都在这**：`ops-topic` 明令「没有热点简报不要自己扫热榜」，
> 所以「热点没更新过」的口子必须由 P4 引到 `ops-signal`，否则这条路径是死路。

优先级是默认路由，不是死锁。用户明确指定“先做 X”时，按用户指定走，但要把跳过的前置风险说清楚。

## 阶段契约

每一段只认自己的输入、产出和完成信号。不要跨段偷做。

### 1. Intake — 物料入库

- **进**：`ops/materials/` 里有文件还没登记，或登记了但没描述。
- **做**：一个文件一条 `material`，写清「这是什么」；判不出的留空并问人。
- **出**：台账里每个物料文件都有记录，Agent 挑素材时有依据。
- **不做**：不建 `asset`（那是成品，`ops-produce` 的事），不搬文件。
- **交接**：入库完成后回到主控；是否立刻做选题看用户意图和方向是否清楚。
- **Skill**：`ops-intake`

### 2. Direction / Benchmark — 方向与参照

- **进**：用户给了模糊方向、账号冷启动、或现有方向缺数据支撑。
- **做**：方向拆解、阶段打法、对标候选与拆解。
- **出**：`directions` / `benchmarks` / 可复用 `rules` / 候选 `topics`。
- **门槛**：候选对标、方向修订、起号打法要让用户确认后再落“生效”状态；候选可先落库但要标清状态。
- **Skill**：`ops-direction`、`ops-benchmark`、`ops-benchmark-analysis`

### 3. Topic — 选题

- **进**：方向明确，有素材/规则/热点/对标输入。
- **做**：判断值不值得做，给出选题记录。
- **出**：台账里的 topic，带判断依据。
- **门槛**：不写正文、不画封面、不改已有选题状态。用户点头后才进入制作。
- **Skill**：`ops-topic`

### 4. Produce — 制作

- **进**：用户确认的 topic，或用户明确点名的素材。
- **做**：按形态出正文/脚本/封面/配图/视频，更新 progress。
- **出**：内容成品落盘，asset 变 `ready`（或明确阻塞原因）。
- **门槛**：形态/画幅未定不调付费生成；不伪造完成；不自己改 `form/formAspect`。
- **Skill**：`ops-produce`

### 5. Schedule — 排期

- **进**：`ready` 素材，用户给了时间或要求排期建议。
- **做**：写 `scheduledAt` / `platform`。
- **出**：素材有明确投放时间和平台。
- **门槛**：排期不是发布。不要写“到点自动发布”。
- **Skill**：`ops-schedule`

### 6. Publish — 发布

- **进**：`ready` + `scheduledAt` 到点 + 当前会话有浏览器面板 + 用户明确同意本次发布。
- **做**：通过 `hamuna browser publish` 发布并回读核实。
- **出**：`published`（有回读证据）或 `unverified`（发出但核实失败）。
- **硬门槛**：
  - 只有 `hamuna browser publish` 是合法发布动作。
  - 没有浏览器面板就不发布。
  - 没有回读证据不写 `published`。
  - 心跳、定时任务、无人值守流程不能替用户点击发布。
  - 一轮只发当前确认的那条，不顺手批量发。
- **Skill**：`ops-publish`

### 7. Review — 复盘

- **进**：已发布/已投放素材有表现数据或评论线索。
- **做**：录 reviews、提 clues、沉淀 rules。
- **出**：可复用规则和下一轮选题缺口。
- **门槛**：不编数据；样本弱就低 confidence；过期规则不能直接当依据。
- **Skill**：`ops-review`

## 状态与检查点

台账状态是事实来源；聊天里的“感觉做完了”不是。

| 对象 | 关键状态/字段 | 谁能推进 | 说明 |
|---|---|---|---|
| Topic | 选题记录、状态 | 用户确认进入制作；Agent 不擅自改状态语义 | 选题是决策记录，不是成品 |
| Asset | `draft` / `ready` / `published` / `unverified` （只有这四个） | 子 skill 按规则通过 CLI 更新 | `ready` 只表示可投放，不表示已投放 |
| Schedule | `scheduledAt`, `platform` | `ops-schedule` | 到点是触发提醒条件，不是发布完成 |
| Review | `reviews` / `clues` / `rules` | `ops-review` | 规则要带采样/置信度/过期意识 |

用户检查点默认保留在这些地方：

- 方向/对标候选：人点头才当作生效依据。
- 选题：人选了才做。
- 发布：人明确同意且有面板才发。
- 方向修订：有数据才提，没数据不提。

## 调度策略

### 用户在场的会话

用户在 Chat 里时，主控可以一路推进，但每过一个检查点都要短报：

- 现在卡在哪一步
- 刚完成了什么（用台账事实）
- 下一步要做什么
- 需要用户拍板的只有哪一个点

不要把“我准备做”说成“已经做完”。

### 心跳 / 定时任务 / 无人值守

无人值守只能做**低风险巡检和提醒**，不能假装有人类在场。

允许：

- 扫台账，发现到点未发、待复盘、缺选题。
- 生成简短提醒，写入用户可见的汇报。
- 做不依赖浏览器面板的只读分析或台账查询。

禁止：

- 发布、点浏览器发布按钮、登录账号、改账号设置。
- 绕过 `hamuna browser publish`。
- 把“到点了”说成“已发布”。
- 在没有面板时尝试发布后静默失败。

如果发现 `ready && scheduledAt <= now`：

```text
有素材到点：<asset> / <platform> / <scheduledAt>。
当前是无人值守或无浏览器面板，不能代发。
需要你在有面板的 Chat 里确认后，我再走 ops-publish。
```

## 交接格式

从主控切到子 skill 前，内部要明确三件事；切回主控时也要汇报三件事。

**切出去前**：

- 目标：这一步要把什么状态推进到什么状态。
- 输入：用哪条 topic/asset/rule/benchmark。
- 停止条件：做到哪一步必须回来。

**切回来后**：

- 事实：台账里什么变了（id、状态、关键字段）。
- 卡点：没做成的原因，不脑补。
- 下一跳：建议交给哪个子 skill，还是等用户。

对用户汇报时，一句话讲结果，一句话讲下一步。不要复述子 skill 的字段清单。

## 失败与恢复

| 情况 | 处理 |
|---|---|
| 台账读不到 / CLI 报错 | 停下，报原始错误摘要；不猜状态、不手改 state.json |
| 子 skill 半途失败 | 以台账实际状态为准，标明已完成和未完成；不要重置已成功写入 |
| 发布已提交但回读失败 | 按 `ops-publish` 写 `unverified`，列出缺的证据，等人工核实 |
| 定时任务触发但无面板 | 只提醒，不发布 |
| 规则/方向过期 | 降级为待验证，不直接驱动制作 |
| 用户指令与硬门槛冲突 | 服从硬门槛，解释原因，给合法替代路径 |

## 不要做

- **不要跳过子 skill 的硬规则。** 主控负责路由，不负责豁免。
- **不要直接编辑 `ops/state.json`。** 见 `05-OPS.md`。
- **不要把排期当发布。** `scheduledAt` 到点 ≠ 已发出。
- **不要在无人值守场景发布。** 没面板、没用户确认、没回读证据，都不行。
- **不要跨段偷跑。** 选题阶段不写正文；制作阶段不改选题状态语义；复盘阶段不编数据。
- **不要批量顺手处理高风险动作。** 发布、方向修订、规则生效这类动作逐条确认。
- **不要用“应该已经”代替事实。** 看 CLI、看回读、看台账。
- **不要无限循环。** 一轮推进后给出明确状态：完成、阻塞、或等待用户。
