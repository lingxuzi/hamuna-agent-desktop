# ops-review — 复盘

复盘有两个产出，别只做前一半：

1. `reviews` — 这条内容的表现数据（事实）
2. `rules` — 从多条事实里看出来的规律（结论）

只填数据不提炼规律，等于把台账当记账本。台账的意义是让下一轮做得更好。

## 数据从哪来

**数据页我能读。** 登录态读自己这个账号的后台在红线允许的范围里（作品列表、数据页、评论页），
见 `05-OPS.md` 的「采集边界」。读得到就自己读，读不到再问用户要。

所以标准流程是：

1. **先自己读** —— 进创作者后台的数据页（`hamuna platforms <id> --json` 里的 `analyticsUrl`；
   这个字段没核实过，就从 `creatorHomeUrl` 出发用 `hamuna browser open` 现场找入口，
   找到把路径记进 `memory/topics/<平台>.md`），`hamuna browser read` 取数字
2. **读不到就问** —— 请用户给截图 / 数字
3. 把数字录进去

**绝不编数据。** 空着比填假的强得多。

## 数据口径

| 字段 | flag | 口径 |
|---|---|---|
| 播放 | `--views` | 整数 |
| 点赞 | `--likes` | 整数 |
| 评论 | `--comments` | 整数 |
| 转发 | `--shares` | 整数 |
| 收藏 | `--saves` | 整数 |
| 涨粉 | `--followers` | 这条内容带来的**净增** |
| 完播率 | `--completionRate` | **0–1 的小数**（41% 写 `0.41`）。平台不给就**不传**——传 0 会被当成完播率为零 |
| 观众原话 | `--commentSample` | 这条内容下面**一条**评论的**原文**。留原话不改写 |

## 录数据

新建一条复盘：

```bash
hamuna ops add review \
  --asset-id asset-1a2b3c4d \
  --platform douyin \
  --published-at 2026-11-10T20:00:00+08:00 \
  --views 12000 --likes 340 --comments 28 --completionRate 0.41 \
  --commentSample "这个折叠桌多少钱？"
```

数据会变（发布后 24h / 72h / 一周各不同）。补数据用 `update`，只传变化的字段：

```bash
hamuna ops update review --id review-1a2b3c4d --views 45000 --likes 1200
```

其余指标由后端合并保留，不会被清空。

用户描述补充结论写 `--note`。

**`--commentSample` 只留一条**，挑最能代表这条内容的那句（问价的那句、被夸的那句、
吐槽的那句都行）。留它的理由：复盘结论的证据常常就是这一句话。下次要复核
「有多少人问价」，光有一个数字谁也复核不了，得有原话。**原文照抄**，不改写、
不翻译——改写过的评论没法拿去回看。评论长的时候用 `--comment-sample-file <路径>`。

## 读评论 → 记线索

同一次进后台，把**我们作品下面的评论**也读一遍。

那是观众的真实反应：问价格、问在哪买、问怎么用 —— 都是需求信号，比任何热点榜都准，
而且是**落在我们自己的内容上**的信号。

```bash
hamuna ops add clue --platform xiaohongshu --comment-id "c-abc123" \
  --asset-id asset-1a2b3c4d --author-name "露营小王" \
  --content "这个折叠桌多少钱？" --intent price
```

- `--comment-id` **必填**（平台侧 id，天然键的一半）。读不到 id 就**别记** —— 没有它，
  下一次采集会变成两条，「多少人问价」就被灌上假数。
- `--asset-id` 能对上就填，对不上就不填（填错比不填更坏）。
- `--intent` 只能是 `price` / `where` / `howto` / `other`。判不出就 `other` ——
  猜一个具体的会把后面的统计带歪。
- `--content` 留原文，不要改写、不要翻译。
- **只读，不回。** 回复评论是人在做的事（见 `02-SOUL.md` 的边界）。
- 别人作品的评论区不碰 —— 那是别人的数据。

线索攒够了就是选题的输入（`ops-topic`）。

## 提炼规律

看的是**跨条目的差异**，不是单条的绝对数。几条素材里：

- 都用了某个做法、数据都好 → 强信号
- 一条明显好、其他都差，差别在某个具体动作上 → 要归因到**那个动作**，不是"这条运气好"
- 全都很差 → 问题可能在选题或形式层，不在执行

写了就落库：

```bash
hamuna ops add rule \
  --name "开头 3 秒给数字" \
  --rule "标题 / 前 3 秒抛出具体数字，比抽象描述起量明显" \
  --source reflection \
  --status proposed \
  --basis inference \
  --confidence 0.4 \
  --sampledCount 3 \
  --evidence "11/03 那条 12 万播放 vs 同题材平均 2 万；11/09 复现一次" \
  --gap "只有 3 条样本，没有跨平台对照" \
  --evidence-bar '{"name":"有数字","val":"1.8×","pct":100}' \
  --evidence-bar '{"name":"无数字","val":"1.0×","pct":56,"mut":true}'
```

规则写法的硬要求：

- `--rule` 要**能直接指导下一次制作**。"要更用心"不是规则。"前 3 秒给数字"是规则。
- `--confidence` 按样本量给：1 条样本 ≤ 0.3，2–3 条 0.5 左右，多次复现才给 0.7 以上。别硬写 0.9。
- `--sampledCount` 是**样本量** —— 这条结论看了多少个样本。`--confidence` 是分值，
  `--sampledCount` 是分母。不写样本量，那个 0.4 是自说自话：下一轮没人知道它是看了
  1 条还是 40 条。看了几条就写几条，**别把读过的评论条数当成样本量**（样本是作品，
  不是评论）。
- `--gap` 写**这条结论还缺什么**，一条一句，可以重复传。例：
  `--gap "评论只读到前 20 条，共 87 条"`、`--gap "没有同题材对照组"`。
  **没看到的东西写在这里，别猜数字填。** 缺口只写在上下文里的话，下一轮就蒸发了 ——
  台账里留着，下一轮才知道还欠什么。
- `--basis` 标这条结论**凭什么这么说**。`--confidence` 是强度（多可信），
  `--basis` 是种类（凭的是什么）——一个 0.9 的推断仍然是推断，光给强度，
  面板上分不出「核实过的 0.5」和「推出来的 0.9」哪个更该当依据。四个值：

  | 值 | 什么时候用 |
  |---|---|
  | `verified` | 平台侧数据对得上，或我回读核实过 |
  | `author_report` | 人（或作者）自己说的，我没独立核实 |
  | `inference` | 从已有数据推出来的，合理但没有直接对照 |
  | `unresolved` | 还没有结论，先占个位 |

  **判不出来就写 `unresolved`。** 把推断标成核实过，比标错更坏——面板上
  「已核实」会让人当既定事实照着做。
- `--evidence` 写**具体对照**（哪个 vs 哪个、差多少），不写"感觉更好"。
- `--evidence-bar` 是**对照条**：`val` 是展示值，`pct` 是条长 0–100（不是原始数值）。只有有对照组的规则才给，对照组那条加 `"mut": true`。
- 新规则一律 `--status proposed`。攒够证据后由用户升 `active`，或你提议、用户点头：

```bash
hamuna ops update rule --id rule-1a2b3c4d --status active
```

## 回馈下一轮

在 `memory/topics/<系列>.md` 记一笔：这轮的结论、下轮要注意什么。别只写进台账——台账记事实，记忆记为什么。

然后按 `active` 规则开下一轮 `ops-topic`。

## 不要做

- **不编数据。**
- 不因为两条数据就下强结论，也不因为样本少就拒绝说 — 给低 `confidence`，别不给。
- **不要直接编辑 `ops/state.json`。**
