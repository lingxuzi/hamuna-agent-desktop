# ops-topic — 选题

选题是四段循环的第二段：**`ops-signal` 产出热点简报 → `ops-topic` 决定做不做 → `ops-produce` 做内容**。

它的产出**只是一条记录**：做什么、为什么值得做、从哪个平台来、参考是什么。
真正写不写、写成什么样，在 `ops-produce`。

## 开工前先读

```bash
hamuna ops list direction --json   # 账号定位：七维里「账号匹配」的基准
hamuna ops list topic --json       # 现在有什么选题、哪些角度已经做过
hamuna ops list rule --json        # 复盘沉淀下来的规律
```

读 `03-USER.md` 拿平台清单和赛道。`source`、`status`、`platform` 的口径见 `05-OPS.md`。

没有 `direction` 时先跑 `ops-direction` 定方向，不要在没定位的情况下批量出题。

## 输入从哪来

| 输入 | 从哪来 | 怎么用 |
|---|---|---|
| 热点简报 | `ops-signal` | 热点候选的阶段 / 关联度 / 角度 / 风险 / 原始链接已经判过；这里只做选题决策，不重扫榜 |
| 评论线索 | `ops list clue --json` | 未处理的 `intent=topic` 线索，优先看；它们是观众自己说想看的 |
| 对标账号 | `ops list benchmark --json` | 看对手最近在做什么、哪里能做出差异 |
| 对标爆款清单 | `ops list topic --json` 里 `source=benchmark` 且 `sourceRefs` 是作品链接的那几条 | 拆解时顺手落的「他最近真的爆了的那几条」，拿具体钩子和封面去改 |
| 复盘规律 | `ops list rule --json` | 只拿 `active` 且验证过的规则当硬约束；`draft` 只是提醒 |
| 用户直接给的题 | 对话 | 用户点名的题目，跳过发现，直接进判断 |

**没有热点简报时，不要自己去扫热榜。** 需要热点输入就先跑 `ops-signal`。扫榜要有浏览器面板，
而面板属于一个正在屏幕上打开的 Chat 会话 —— **没有定时任务替你扫**，别等一个不会来的东西。
无人值守轮次里确实需要扫，通道和约束见 `ops-signal` 的 `hotlist-sources.md`。

## 选题怎么来

**一次出一批，不是撞上一个算一个。** 一次只评估眼前那一个热点，判断再准也只是
「在默认选项里选」。一条值得做的题，前提是它在一堆候选里排得靠前。

顺序是：**先出一批候选（覆盖多个来源）→ 逐条过四道硬门 → 剩下的打分排序 → 留最优那一条**。
「批怎么出」「五类来源各自挖什么」「撞题怎么处理」「多个候选怎么排」见
`references/candidate-batch.md` —— 这一节只列来源，方法在那边。

五类候选：

1. **热点简报**。拿 `ops-signal` 给的候选，逐条过下面的四道硬门和七维打分。简报里已经标
   「不建议蹭」的，不要重新捞回来硬做，除非你有新的证据推翻原判断——推翻时把证据写进 `--note`。
2. **评论区线索**。`ops list clue --status new --json` 里 `intent=topic` 的条目，是观众直接告诉你的需求。用完把线索标成 `used` 或 `archived`。
3. **对标拆解**。扫对标账号最近发了什么，找能借的角度。拆法见 `ops-benchmark-analysis`。
   那边拆解时会顺手落「最近爆款清单」（`source=benchmark` 且 `sourceRefs` 是作品链接），
   直接拿来当候选 —— 那是具体的钩子、封面、开头，不是抽象规律。
4. **存量裂变**。从自己跑赢过的选题里换角度再做一条。前提是那条选题已经有复盘结论，不能凭感觉复刻。
5. **时令 / evergreen 储备**。节气节日（能提前排期，见 `candidate-batch.md` 第三节）和
   不过时的选题，攒着等内容荒的时候顶上。

**扫一轮的覆盖检查**：五类里只用了「热点简报」，这轮候选其实是一张榜的转述。
线索和存量裂变是只有我们有的数据，每轮至少看一眼有没有存货。

热点来的题标 `--source hotspot`，并带上 `--ref <热点简报里的原始链接>`。`--hotness` 只填参考内容的**播放量**；热榜热度值不是播放量，不填。

## 一次最多 3 条候选（硬约束）

**一批候选的上限是 3 条。** 不是「建议 3 条」，是不许更多。

- 提 10 条的产出不是「选择更多」，是「没有选择」—— 每条都只能得到 1/10 的判断力。
- 候选数不够 3 条就少提，不要凑。硬凑出来的第三条会让真正好的那条显得平庸。
- 3 条是**内部候选**的数量，不是推给用户的数量。推给用户的是**一条**，见下面的「自我批判」。

用户当轮明确说「给我三条」「多列几个」，才放开这个上限 —— 那是他要对比，不是要你做决定。

## 四道硬门

候选题逐条过，**任一不过就毙，不进打分**：

| # | 门 | 不过的信号 |
|---|---|---|
| 1 | **关联度** | 这题跟我这个号的定位搭不上边。硬蹭只会让观众困惑。`ops-signal` 已判低 / 无的热点默认不过，除非有新证据。 |
| 2 | **差异化** | 同题材别人已经讲烂了，我没有新角度 / 新信息 / 新表达。判据是**能不能写出一句 `--angle`**：填不出来就是没差异。`hot-riding.md` 的六种切入角度是这句话的来源。 |
| 3 | **可行性** | 需要的素材、权限、时间现在没有，或者做出来也赶不上。 |
| 4 | **合规** | 平台会限流、封号，或者有法律 / 品牌风险。 |

四道门过了才值得花时间打分。门都没过的题，不要记进台账「留着以后看」——那是垃圾堆。

**72 小时不是第四道门，是第五道之外的一条分类规则。** 热点超过 72 小时（长尾期）
就不再是热点题：要么毙掉，要么**改成常青题**（`--source manual`）走正常七维——
别拿它继续挂 `--source hotspot`，那会让复盘统计里的「热点题表现」被一堆冷饭污染。
阶段边界只写在 `ops-signal` 的 `hot-riding.md` 一处，不在这里重复。

## 七维打分

过了硬门的题，七个维度各 1–10 分：

| 维度 | 问什么 |
|---|---|
| 账号匹配 | 符合 `direction` 定的调性、受众、禁区吗？ |
| 受众需求 | 目标观众真的想看这个吗？有搜索量 / 评论问过 / 私信求过？ |
| 竞争度 | 同平台同题材已经有多少条？头部的效果怎么样？ |
| 制作成本 | 要多久、要多少素材、要不要外援？ |
| 变现潜力 | 能带来关注、转化、还是纯消耗？ |
| 时效性 | 现在发和下周发差多少？热点题过了窗口就作废。 |
| 可扩展 | 能不能裂变成系列？一条题能不能长出三条？ |

**不设总分阈值。** 七维里任何一维 ≤ 3 分，单独拎出来说清楚为什么还要做；说不清就毙。

## 自我批判：先把候选毙到自己只剩一条

打分排完序**不要直接推给用户**。排序是「哪条分高」，自我批判是「最推荐的那条怎么才会失败」。
两件事都要做，因为一条题的失败方式通常不在打分维度里。

对排在第一位的那条，逐条回答（写不进答案就是答不上来）：

| 问题 | 答不上来意味着 |
|---|---|
| 这条最可能怎么失败？ | 你还没想到它什么地方会崩，只是觉得好 |
| 同样的话，别人为什么没做？ | 要么有坑你没看见，要么你确实找到空位（要能说出是哪种） |
| 如果扑了，损失的是钱、时间、还是号的定位？ | 损失方式决定值不值得赌 |
| 我的 `--angle` 那句不一样的话，三天后还站得住吗？ | 靠时效撑着的题，三天后就是废题 |

**回答得下来才推。答不下来，就从剩下的候选里换一条重新问。** 三条都答不下来，这轮
就不推选题 —— 明说「这批都不够好」，比硬推一条让用户去改要好。

### 推给用户什么

- **默认只推 1 条**：最优那条，带一句「为什么是它」+ 一句「它最可能怎么失败」。
- **另外两条不推、不删、不落库**。它们是这一轮的推导过程，不是待办。落进台账就会
  在面板上冒充「可选选题」，下一轮你还得再毙一次。
- 用户明确说「给我三个」时，推 3 条并附排序理由 —— 他要对比，这时候自我批判的结论
  改成每条各一句「它最可能怎么失败」。

## 落台账

**只落推给用户的那一条**（用户点名要三条时落三条）。

```bash
hamuna ops add topic \
  --title "用一句话说清这条要讲什么" \
  --platform douyin \
  --source hotspot \
  --angle "专业解读：这条里没人说清的一点是…" \
  --ref "https://原帖或热点链接" \
  --hotness 86000 \
  --note "为什么值得做；七维里哪个维度最强 / 最弱；最可能怎么失败"
```

- `--source` **只有四个值**：`hotspot`（热点）/ `benchmark`（对标）/ `reflection`（复盘回流）/ `manual`（其它，含用户点名、时令、存量裂变）。写别的值会被 store 拒。
- `--angle` **必填**。写成「专业解读：这条里没人说清的一点是 XXX」，不是只写「专业解读」
  —— 四个字是分类，不是角度。下一步 `ops-produce` 就是靠这句话定开头钩子的，空着它只能重新猜。
- `--platform` 是这条选题**计划发在哪个主平台**。
- `--ref` 是可重复的 `sourceRefs`：热点填原帖 / 热榜条目链接，对标填**作品链接**（不是主页）。
- `--hotness` 是参考内容的**播放量**。没有可比参考就不传；**热榜热度值不是播放量，也不传**。
- `--note` 写判断，不写废话。下一轮复盘会读它。

> **没有 `--competitor`。** 对标信息走 `--ref`（作品或主页链接）+ `--note`（哪条对标、
> 借了什么）。CLI 里没有这个 flag，写了会被静默丢弃 —— 不报错，只是没存进去。

## 提给用户

一句话说清这条的核心判断（不是复述标题），加一句「它最可能怎么失败」。用户点头后进 `ops-produce`。

## 不要做

- **不要扫热榜。** 热榜采集、阶段判断、关联度 / 风险初判属于 `ops-signal`。
- **不要在这一步写正文、画封面。** 那是 `ops-produce` 的事。
- **不要改已有选题的状态。** 那是用户在面板上按的检查点。
- **不硬凑热点。** 简报里已经判低 / 无关联的，不要重新包装成「其实有关」。
- **不要直接编辑 `ops/state.json`。**
