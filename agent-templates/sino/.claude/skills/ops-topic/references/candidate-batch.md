# 一批候选怎么出来，怎么排

> **方法论来源**：Beav `desktop/builtin-skills/content-topic-miner/SKILL.md`（五个挖掘方法的分工与默认配比、每次固定产出一批而不是碰运气撞一个、打分入选题池）与 `desktop/builtin-skills/wander-synthesis/SKILL.md`（撞题时「选一个母版拆公式，其余只捐一个细节」，不做三篇素材的平均合并）。
> **改动**：
> 1. **`comment_demand_insight` 换成了 `clue_demand`。** Beav 那个方法读**别人作品**的评论区找需求。sino 的红线是别人作品的评论区不碰，我们只读**观众在自己作品下面**说的话 —— 数据源不同，方法名跟着换。
> 2. **热度那一半没搬。** Beav 的综合分是「热度 60% + 关联度 40%」，它的热度来自一个有热度数值的第三方数据源。sino 的热榜只给标题和榜位、**不给热度值**，而 `--hotness` 的口径是**参考内容的播放量**。所以这里不造综合分，只造**关联度**这一维作为可排序产物，热度用「榜位」当**带标签的代理**、且只在同一张榜、同一次刷新内可比。

> 4. 去掉模型调用和积分口径。

## 一、为什么是「一批」而不是「一个」

一次只评估眼前撞上的那一个热点，判断再准也只是**在默认选项里选**。
一条值得做的选题，前提是它在一堆候选里**排得靠前**，而不是它自己看着还行。

所以顺序是：**先出一批候选（覆盖多个来源）→ 逐条过四道硬门 → 剩下的打分排序 →
自我批判，只留最优那一条推给用户**。
四道门、七维打分、自我批判的四个问题都在 `SKILL.md` 里，本文件只管「批怎么出」和「怎么排」。

## 二、五个来源，各自挖什么

| 方法 | 从哪挖 | sino 里怎么拿 |
|---|---|---|
| `trend_check` | 外部热点、时令、行业事件 | 热榜（`ops-signal` 的 `references/hotlist-sources.md`）；时令见下面第三节 |
| `clue_demand` | **观众在我们自己作品下说出来的需求** | `hamuna ops list clue --json`。同一件事被问 3 次以上才算信号，一条不算 |
| `history_extension` | 我们自己做过、跑过的题，换个切面再做 | `hamuna ops list topic` + `list review`：哪条数据好、好在哪个角度 |
| `knowledge_similar` | 这个号已经会的东西，往相近题材外推 | `03-USER.md` 的赛道 + `memory/topics/` 里沉淀过的做法 |
| `collision` | 两个不搭边的东西撞一起，撞出一个新角度 | 无数据源，靠上面四类里各取一个 collide（规则见第四节） |

**扫一轮的覆盖检查**：如果五个来源里你只用了 `trend_check`，这轮候选其实是**一张榜的转述**，
不是「今天的选题」。热榜是最容易拿到的来源，也最容易变成唯一来源 —— 这是最常见的退化。

`clue_demand` 和 `history_extension` 是**只有我们有的**数据，别的号抄不走。
它们拿不到新热点，但拿得到「别人没有的题」。每轮至少看一眼台账里这两块有没有存货。

## 三、时令：唯一能提前排期的一类热点

`ops-direction/references/pillar-and-cadence.md` 给美食 / 生活方式号分了 15% 给
「节日 / 节气 / 时令」。这一档以前没有数据源 —— 下面就是。

它和热榜是**两种完全不同的东西**：

| | 热榜热点 | 节气 / 节日 |
|---|---|---|
| 什么时候知道 | 爆发后 0–4 小时 | **提前几个月就知道** |
| 能不能排期 | 不能，只能抢 | 能，而且该提前排 |
| 半衰期 | 几小时到几天 | 当天集中，前 3–7 天的筹备期才是机会 |
| 素材 | 现场找 | 能提前备 |

**这意味着时令不该等「到那天才想起来做」**，而该在**排期阶段**就被看见：
提前 3–7 天把内容做出来，在节前 1–2 天发（多数节日的搜索/浏览高峰在节前，不是当天）。

### 二十四节气（公历月份窗口，不是精确日期）

`立春 雨水`(2) · `惊蛰 春分`(3) · `清明 谷雨`(4) · `立夏 小满`(5) · `芒种 夏至`(6) ·
`小暑 大暑`(7) · `立秋 处暑`(8) · `白露 秋分`(9) · `寒露 霜降`(10) · `立冬 小雪`(11) ·
`大雪 冬至`(12) · `小寒 大寒`(1)

**精确日期不背。** 每个节气落在公历 5–7 号或 20–23 号之间浮动，具体哪天现场查。
写错一天等于把内容发在没人搜的那天。

### 固定公历节日（可提前排）

元旦 1/1 · 春节（农历，每年不同，**必须查**）· 情人节 2/14 · 妇女节 3/8 · 劳动节 5/1 ·
母亲节（5 月第二个周日，**要算**）· 儿童节 6/1 · 父亲节（6 月第三个周日）· 七夕（农历）·
中秋（农历）· 国庆 10/1 · 双十一 11/11 · 双十二 12/12 · 圣诞 12/25

**农历节日和「第几个周日」都不背日期**，现场查。`2026` 这种年份在 prompt 里写死，明年就错了。

### 时令怎么用

1. 先看**这个月有什么**（节气 + 节日 + 当季食材）：现在离哪个还有 3–7 天。
2. 判断和定位有没有关系 —— **过门，不过门不做**。春节不是「红底金字」，是「这个时候大家真的在做什么」
   （`ops-produce/references/visual-director.md`「四、节日与事件借势」）。
3. 提前做出来，**排期排在节前 1–2 天**，别排当天。
4. 灾难 / 事故 / 逝世类日期不借（`hot-riding.md`「风险」）。

## 四、撞题（collision）：选一个母版，不是取平均

把两个东西对撞的时候，最容易做错的形状是「A 也有道理，B 也有道理，把它们合起来」——
**合出来的东西两头都不像，也两头都不够sharp。**

正确做法：

1. **选一个母版** —— 两个来源里更有流量、结构更成型的那个，拆出它的公式
   （它靠什么钩子、什么结构、什么承诺）。
2. **另一个只捐一样东西** —— 一个细节、一个场景、一个反差。**不捐结构**。
3. 写出来之后自检：
   - 我有没有把母版的公式换掉？（换了就不是撞题，是另起一个）
   - 另一个来源是不是被硬塞进来的？（塞进去的部分删掉有没有损失？没损失就删）
   - 题是不是还是太大？（「露营装备怎么选」是没撞过的原题；「第一次带娃露营只带三件」才是撞出来的）

撞题不是把两个题拼起来，是**用 A 的骨架装 B 的一块肉**。

## 五、排序：关联度是本地算的，热度只借榜位

七维打分里已经有账号匹配和流量潜力。这一节只说**多个候选之间怎么排**，因为
推给用户之前必须能排出前后 —— 排不出第一名，自我批判就没有对象。

```markdown
| # | 候选 | 来源 | 关联度 | 榜位 | 七维 | 结论 |
|---|---|---|---|---|---|---|
| 1 | 小雪节气炖锅 | trend_check | 高 | —（节气，无榜位） | 78 | 提 |
| 2 | 某明星火锅店 | trend_check | 低 | 3 | 41 | 毙（关联度低） |
| 3 | 上周那条的续集 | history_extension | 高 | — | 71 | 提 |
```

**关联度（高 / 中 / 低 / 无）是本地的判断**，来自 `03-USER.md` 的赛道和 `direction` 的定位 ——
它不需要外部数据，**所以它永远是这一列里最可靠的那一维**。低 / 无直接毙，不进排序。

**榜位可以当代理，但必须带标签：**

- 只在**同一张榜、同一次刷新**内可比。不同榜的位次之间没有可比性。
- **不许换算成数、不许填进 `--hotness`。** `--hotness` 的口径是参考内容的播放量，
  要填就打开 `items[].url` 那条具体内容去读播放量，读不到就不传。
- 榜位只影响「先看哪条」，不影响「提不提」。提不提由四道门 + 七维定。

**没有榜位的候选（时令、历史延伸、线索）不因此吃亏。** 它们本来就不在榜上，
拿「不在榜上」当扣分理由，等于把五个来源压回成一个。
