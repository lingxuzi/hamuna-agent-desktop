# ops-direction — 运营方向

每个平台一条方向。它回答**这个号是什么**，不回答**这一条内容怎么写**。

方向回答四件事：写给谁、和别人不一样在哪、靠哪几条内容支柱撑起来、要达成什么。
选题（`ops-topic`）判断「这个题值不值得做」时读的正是这几条 —— 方向错了，
选题挑得再准也是在错的赛道里跑得很快。

## 开工前先读

```bash
hamuna ops list direction --json    # 这个平台现在有没有方向，是不是已有 active
hamuna ops list rule --json         # 复盘沉淀的规律，方向要能解释它们
```

再读 `03-USER.md` 的 identity / audience / cadence 三节。**那是用户自己填的，
方向不能和它矛盾** —— 矛盾时以 `03-USER.md` 为准，把差异说出来，别自己改用户填的东西。

## 两个动作，先分清

| 现状 | 你该做什么 | 为什么 |
|---|---|---|
| 没有这条记录，或 `status: draft` | **直接写回**（`--positioning` 等） | 用户点了「交给 Agent 整理」，意图就是「你来定」。再让他点头一次是把活推回去。 |
| `status: active`（方向已经定过） | **提修订**（`--proposal`），等人采纳 | 已经跑起来的方向是用户的既定决策。改它必须他点头。 |

判断依据只看 `status`，别看「这次改得多不多」。改一个词和改整段同样需要点头 ——
人的注意力成本不在字数上。

## 冷启动：把模糊原话拆开

用户的原话通常是「想让人记住我们懂露营装备」。这句话包含定位的种子，不含受众、支柱、
目标和节奏。你要补的是**他自己没说但一定会同意**的部分，不是发明一个新赛道。

四步：

1. **定位**（`--positioning`）— 一句话，说清「我是做 X 的，我的差异是 Y」。
   不许出现「优质」「专业」「用心」这类谁都装得下的词 —— 那是没定位。
2. **受众**（`--audience`）— 具体到「谁在什么场景下会看」。写「想买第一套露营装备但
   嫌贵又怕买错的都市白领」而不是「年轻人」。说不清场景就没有受众。
3. **内容支柱**（`--pillar`，2–4 条）— 反复出现的栏目骨架，不是选题清单。
   「装备测评」「露营场景」「翻车复盘」是支柱；「帐篷怎么选」是选题。
4. **目标 + 节奏**（`--goal` / `--cadence`）— 目标写成可验的数字或状态
   （「3 个月到 5000 粉」不是「涨粉」）；节奏从 `03-USER.md` 抄，那里填了就别改。

**一次落齐，不要分批。** 半张方向比没有方向更糟：选题会读到一个残缺的定位。

方向定完，**下一步是定对标账号**（`ops-benchmark`）—— 方向说「我们要往哪走」，
对标说「走这条路时旁边那个人长什么样」。没有对标，选题会退化成凭空想。

```bash
hamuna ops update direction --platform douyin \
  --positioning "夜间露营装备的实测与避坑，只讲我真用过的东西" \
  --audience "想入门露营、预算有限、怕买错的都市通勤族" \
  --pillar 装备实测 --pillar 夜间场景 --pillar 翻车复盘 \
  --goal "3 个月内产出 30 条实测，涨粉到 5000" \
  --cadence "一周 3 条，晚 20:00 发" \
  --status active
```

**第一条记录用 `update` 而不是 `add`**：`update direction --platform douyin` 在记录不存在时
会建一条，在存在时就改它 —— 同一个命令两种情形都对，不用先探一次。`add` 需要
`--platform`，语义是「这条还不存在」，探错了就白跑一轮。

`--pillar` 可以重复传，也可以传多个值。**不要用逗号分隔一个 `--pillar`**：
那会变成一条叫「装备实测,夜间场景」的支柱。

## 起号：从 0 开始的打法

方向回答「这个号是什么」，**起号回答「这个号怎么从 0 走到第一个 1000 粉」**。
落的是同一条记录（`directions`），但起号多两样东西：**当前处在哪一档**，
和**接下来这批内容发什么**。

阶段标尺与分阶段处方见 `references/launch-stages.md`；
支柱配比与发布频率见 `references/pillar-and-cadence.md`。

### 先看我们在哪一档

```bash
hamuna ops list review --json    # 最近一条的 metrics.followers = 当前量级
```

一条复盘都没有 = 0 档（冷启动）。阶段不同，处方完全不同：

| 阶段 | 这一档该做的 |
|---|---|
| 0-500（冷启动） | 定位收窄到一个细分 → 拆同层对标 → **统一一个选题方向发 10 条测试** → 看哪类进了小流量池 |
| 500-5k（起量） | 把测试出的高互动模型固化成模板 → 固定更新节奏 → 每条强化前 3 秒钩子 |
| 5k-1w（放大） | 系列化 + 爆款结构复用 → 主页/结尾优化关注转化 → 沉淀选题库 |
| 1w+（沉淀） | 私域 / 变现 / 矩阵铺号 |

### 0-500 的依据：对标的涨粉逻辑

起号方案不能凭空定。**先拆对标，再照着能借的那一条定。**

```bash
hamuna ops list rule --json     # 找 source: benchmark 的规则
```

`ops-benchmark-analysis` 拆出来的那条规则，写的就是「他靠什么涨粉」。
它是**竞品规律**，在台账里的权重跟「我们自己复盘出的规律」不同 ——
它描述的是对手在做什么，不是我们该照抄的。所以：

- **能借的只有一条**：他涨粉的那条通路（爆款拉新 / 稳定输出 / 系列养粉）。
  七维全搬过来 = 没拆过。
- **只当依据，不当铁律**：他这么做有效，不等于他这么做是因为他这么做。
  等我们自己的复盘验证过、那条规则 `status` 转 `active` 之后，才配当筛选条件。
- **同层才叫同层**：台账里的对标规模通常更大。0-500 档要同层参照，
  在 `evidence` 里读规模，够小才用；不够就补一个量级接近的（见 `launch-stages.md`）。

### 落地：goal / cadence / pillars

起号方案落回 `directions` 那条记录。还没定过的（`draft` 或不存在）直接写，
已经 `active` 的提修订等人点头：

- **`--goal`** 写成带期限的数字：「3 个月到 5000 粉」，不是「涨粉」。
- **`--cadence`** 写频率 + 支柱配比：「一周 3 条，晚 20:00 发；配比 干货 30 / 故事 25 / 案例 20 / 观点 15 / 推广 10」。
  频率按平台 × 阶段查 `pillar-and-cadence.md`。
- **`--pillar`** 2–4 条，配比按 `03-USER.md` 的创作者类型查基线。

**0-500 档先别配比。** 那一档要发的是「统一一个方向的 10 条测试」——
10 条里塞 3 个方向，等于什么都没测出来。配比是**测试之后**、
确定哪类进了小流量池再谈的事。

### 前 10 条测试选题

测试选题交给 `ops-topic` 出（它有七维打分和落库）。这一段只定两件事：

1. **统一哪个方向** —— 一个，写进 `--note`。
2. **10 条发完看什么** —— 哪几类进了小流量池。这一档就过了；
   一条都没进，换方向再测一轮，不是加量，是换变量。

## 修订：跑过几轮之后

修订的触发不是「我觉得可以更好」，是**数据说了点什么**：

- `rules` 里有一条 `confidence >= 0.5` 的规律指向「这个方向该扭」（例如「晚间内容
  表现是早间的 2 倍」→ 节奏 / 场景支柱要动）
- 同一支柱连做 5 条都起不来，另一支柱偶然发一条就爆了
- **跨档了** —— 粉丝量级过了 `launch-stages.md` 的档位线，那一档的处方换了
  （0-500 的「统一方向发 10 条测试」到 500-5k 的「固化成模板 + 固定节奏」），
  `goal` / `cadence` 得跟着换。跨档的依据是最近一条复盘的 `metrics.followers`，
  把它写进 `rationale`。
- 用户自己要宣传的产品变了（`opts` / `03-USER.md` 的 Context 变了）

**没有数据支撑的修订不许提。** 「我觉得定位可以更清晰」不是修订理由，是没话找话。

修订是**完整的新值**，不是差异 —— 人看到的是「改成这样」，点采纳就整段替换：

```bash
# 四个多行字段塞进 shell 引号是灾难，写成文件再传
cat > /tmp/direction-proposal.json <<'JSON'
{
  "positioning": "夜间与雨天露营装备的实测，只讲我真用过的",
  "audience": "想入门露营、预算有限、怕买错的都市通勤族",
  "pillars": ["装备实测", "夜间与雨天场景", "翻车复盘"],
  "goal": "3 个月内产出 30 条实测，涨粉到 5000",
  "cadence": "一周 3 条，晚 20:00 发",
  "rationale": "复盘的 8 条数据里，晚间与雨天场景的完播率是其他场景的 1.9 倍"
}
JSON

hamuna ops update direction --platform douyin --proposal-file /tmp/direction-proposal.json
```

- `rationale` **必填**，一句话说清「为什么现在该改」。面板会把这句话直接显示给用户，
  它是他决定点不点的唯一依据。
- `evidence` 可选，填数据出处（「review-1a2b3c4d 等 8 条，样本 2026-11-01～11-14」）。
- **提完就停。** 不要自己 `--accept-proposal` —— 那个键在 Rust 侧是原子动作，
  但它是**人的**动作。你提、他采纳，这是这个功能存在的全部理由。

## 什么时候不该动方向

- 只在某一个平台跑出了新规律 —— 改那个平台那一条，不要一改全改。每个平台面的人是不同的。
- 阶段性的选题调整（这周多做几条某类型）—— 那是 `ops-topic` 的事，不是方向变了。
- 用户临时说「今天发点轻松的」—— 单条内容的事，别上升成方向。

## 交接

写完或提完，一句话说清**你定了什么、依据是什么**。不要复述字段。

- 冷启动：「douyin 方向定了：夜间露营实测，受众是预算有限的入门者，三条支柱 X/Y/Z。
  依据是你在 `03-USER.md` 写的赛道 + 原话里『懂露营装备』。」
- 起号：「douyin 处在 0-500 档。定了 3 个月到 5000 粉、一周 3 条晚 20:00、
  支柱 装备实测 / 夜间场景 / 翻车复盘。前 10 条统一发『装备对比』这一个方向，
  看哪几条进了小流量池。依据是拆@露营老张 —— 他靠对比类爆款拉新，我们借这一条。
  方向还没定稿，你点头我写进台账。」
- 提修订：「提了一条 douyin 修订：把场景扩到雨天。依据是 8 条复盘数据里雨天场景完播率
  1.9 倍。面板上点采纳就生效。」

## 不要做

- **不直接编辑 `ops/state.json`。** 一切写操作走 `hamuna ops`（见 `05-OPS.md`）。
- 不自己造 `id`。方向记录按 `platform` 定位，id 由后端从平台派生。
- 不改 `03-USER.md` 里用户填的内容。要改先说出来，他同意再动。
- 不为「方向更完善」提修订。没有数据就是没有依据。
- **不把竞品规律当自己的规律用。** `source: benchmark` 的规则是依据，不是筛选条件；
  已经是 `active` 的竞品规则才例外（那说明我们验证过了）。
