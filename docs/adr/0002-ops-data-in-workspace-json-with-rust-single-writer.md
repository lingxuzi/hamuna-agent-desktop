# 运营数据存工作区 JSON，写入收敛到 Rust 单一写者

运营视图能独立增删改、Agent 也能改同一份数据，两个写者会撞车。解法不是让两边抢着写文件，而是把写入收敛到一个 chokepoint：Rust 侧的 `OpsStore` 负责字段校验、原子写与文件锁；渲染器走 Tauri invoke，Agent 走 `hamuna ops` CLI → 管理 API。落盘文件留在工作区里（`ops/state.json`），人类可读、可 git。

## Considered Options

- **Agent 唯一写者，视图的改动转成对话消息**：每次编辑都变成一次 LLM turn，慢，而且模型会改写用户原意 —— 运营台账里"把标题改成 X"这种操作不该被再创作一次。
- **渲染器与 Agent 各写各的**（一边 CAS、一边共享锁文件）：跨进程要发明一套锁协议，比复用既有模式引入的新概念更多。
- **KB 的 SQLite**：`kb` MCP 工具只有只读的 `kb_query`，没有任何结构化写入路径，要另建表 + 另建写工具 + 另建 Agent 侧调用面。

## Consequences

- 运营数据的位置由工作区决定，不是全局单例：换工作区 = 换一份运营台账。
- Agent 不再用文件工具直接写 `ops/state.json`，必须走 CLI —— 与定时任务同一条纪律（定时任务历史上就是因为让 AI 有旁路才把 `im-cron` MCP 下线）。
- 工作区里的这份文件是**投影出来的权威**，不是"随便一个 JSON"：谁都能读，但它不是可随手编辑的中间格式。
