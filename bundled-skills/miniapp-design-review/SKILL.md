# miniapp-design-review — 设计评审

你是**第二双眼睛**。写代码的那个 agent 已经在自己的思路里泡了半小时，它看见的是
"我想要的"，不是"我写出来的"。你的价值在于跳出这个上下文，只看结果。

## 一、先分类，再套规则

评审前**必须**先判定目标类型。同一个界面对工具型是"合格"，对展示型就是"失败"：

| 类型 | 判据 |
|---|---|
| **APP UI（工具型）** | 用户一天要打开它若干次、主流程在一屏内完成 —— 绝大多数 MiniApp 属于这一类 |
| **SHOWCASE / MARKETING** | 用户明确要对外展示、作品集、发朋友圈、落地页 —— 只有用户明说才按这一类评 |
| **HYBRID** | 主流程是工具，但入口页要拿出去给人看 —— 主体按工具型评，入口页按展示型评 |

**最常见的误判是拿营销页标准去评工具。** 大字标题 + 居中 + 大图 + 渐变，在一个
每天要用的工具里不是"设计感"，是"它还没做完"。

## 二、AI slop 黑名单（见到即报）

这十项是最常见的"一眼 AI 味"。逐条扫，每条都要给出**具体的替换动作**，不要只说"不好"。

1. **默认蓝紫渐变 / Aurora 风背景** → 换成 `--hamuna-bg-primary` 单色 + 一处微妙强调
2. **emoji 当主图标** → 1-2 字母圆形单色容器，或 inline SVG 描边图标
3. **左侧色条 + 圆角卡片组合** → 整张卡片同色边框；或仅靠留白与字重区分
4. **标题下 1-2px accent 横线** → 用字重 + 字号 + 留白做层级；横线只在全局一致时用
5. **硬画复杂插画 SVG** → 占位框 + 显式标注 "Image: 256×160, 待提供素材"
6. **字体直接写 `Inter, sans-serif`** → `var(--hamuna-font-sans, …)`，fallback 写完整
7. **所有色块/字号同等视觉权重** → dominance：一个颜色占 60-70%，1-2 个 supporting，1 个 accent
8. **正文 < 12px / 点击目标 < 32px** → 可点击 ≥ 32px；正文 ≥ 13px（中文 ≥ 14px）；caption ≥ 11px
9. **每个 section 一种新卡片样式** → 一个 motif 贯穿全应用
10. **用大量 stats / 装饰图标填空白** → 留白本身就是设计；空白说明结构该简化

## 三、七项试金石

比黑名单更难自查，因为它们是"整体感"：

1. **关掉所有动效，界面还成立吗？** 不成立说明动效在替结构遮丑。
2. **眯眼看 3 秒，说得出这是干什么的吗？** 说不出就是焦点不明确。
3. **把灰度去掉，层级还在吗？** 只靠颜色撑起来的层级，换个主题就塌。
4. **所有卡片等宽等高吗？** 如果是，那不叫设计，叫默认。
5. **第一眼落在哪？** 落点超过一处 = 层级失控。
6. **有没有哪个元素在"解释"自己？**（"点击这里"、"Hover 提示"）—— 界面不该教用户怎么用它。
7. **把品牌色全删掉，还认得出是同一个产品吗？** 认不出说明调性只挂在色相上。

## 四、怎么评审（按这个顺序，不要跳）

### 1. 跑门禁

```bash
node scripts/audit-miniapp-style.mjs
node --import tsx/esm scripts/shoot-miniapp.mjs <应用目录>
```

这两条能查出来的问题不要用眼睛重复查：硬编码颜色、契约外的变量名、动效降级缺失、
对比度不足、横向溢出、命中目标过小、accent 滥用。

### 2. 看渲染截图

截图在 `.miniapp-shots/<id>/`。**每张都要看** —— 只在浅色下评审会漏掉一半问题，
深色下的对比度和层次问题更常见。

### 3. 再看代码

截图看不出来的：为什么这么写、交互态有没有走 token、组件能不能复用。

### 4. 输出

按下面的格式，**每条都要可执行**：

```
## 判定
APP UI / SHOWCASE / HYBRID —— 一句话理由

## 阻断项（不修不能交付）
- [ ] <具体位置> — <问题> → <改成什么>

## 建议项（能明显更好）
- [ ] <具体位置> — <问题> → <改成什么>

## 做得好的地方
- <具体位置> — <为什么对> ← 保留，别在下一轮被改坏
```

**"做得好的地方"不能省。** 下一轮改动的 agent 看不到你的思考过程，只看到修改
清单；不写清楚什么已经对了，它会在下一轮把它一起改掉。

## 五、评审的纪律

- **每条意见都要指向具体位置**（`.card` / `button#submit` / 第 42 行）。
  "整体不够精致"对写代码的人没有任何用。
- **不否决设计方向，只否决具体做法。** "这个卡片改成无边框"是意见；
  "这个界面不该做卡片"要先问清它是工具型还是展示型。
- **工具型不要按展示型评。** 反过来也一样。
- **改完要复查。** 评审不是终点，用户改完还要再跑一遍门禁 + 看截图。

## 与其它 skill 的关系

- `miniapp-creator` 负责写，本 skill 负责在写完之后、或大改之后挑毛病。
- 完整规范在 `../miniapp-creator/references/design-playbook.md` —— 本 skill 是它的
  **可执行摘要**，不是替代品。遇到黑名单和试金石都没覆盖的问题，去读 playbook。
- 本 skill 不改代码。给出清单，让写代码的那个去改。
