# 设计方向 — 写样式之前

这份文件管**在动笔之前想清楚什么**。长什么样（token、动效房规、排版、反 AI 味清单）在
[`design-playbook.md`](./design-playbook.md)，两者不重叠：playbook 回答「怎么写才合规」，
本文件回答「这个 app 该长什么样」。

> 方法来自 `bundled-skills/oil-ui/references/design-direction.md`，改写成 MiniApp 场景。
> 保留的是它的推理方式（认品类 → 拆标杆 → 定调性 → 起方向 → 差异检验），砍掉的是
> 对比页、多方案并排、Pro 版推荐那些在这个产品里没有落点的东西。

---

## 为什么需要这一步

模型不被推一把时，给出的是**让所有人都能接受的平均答案**。不是难看的，是正确的：
一屏分三块、每块一个圆角卡片、标题加一条 1px 灰线、底部一排图标。全部合规，
全部及格，没有一处让人记住。

playbook 的反 AI 味清单能挡住**做错**的，挡不住**做得对但平庸**的 —— 清单查的是
"有没有犯忌"，不是"有没有主张"。这份文件补的是后面这个空缺。

**代价对比**：先想清楚再写，比写完再返工便宜。返工时要推翻的不是几行 CSS，
是已经铺开的 DOM 结构和一层层叠上去的样式。

## 一、认品类，拆标杆

动手前先认清这是什么品类，再看这个品类里做得最好的产品怎么做。这给出**地板**：
用户已经习惯的结构，以及一线产品的完成度。调性和方向是在这块地板之上找这个 app
自己的东西。

**1. 说出品类和标杆。** 这是什么品类——正则调试器 / git 图谱 / 塔罗牌阵 / 数据看板 /
文件管理器。**这个品类里风格最鲜明的两三家是谁**（不选最有名的那家）。

**2. 拆一家，拆成 6–10 条看得见的要素。** 每条写两件事：它是什么样，它为什么这样做。
按这几层拆：控件的形状和手感、字体、颜色、图标、状态与反馈、动效、文案语气、
首屏放了什么。

> 拆到能照着做的程度。例：某学习类 App 是"按钮厚实，按下去会陷下去，答对时夸张弹跳"，
> 理由是答题是核心动作，要给利用零碎时间的普通人手感上的回报。
> 某开发工具是"深色、行距紧、每种状态一个统一图标、快捷键印在菜单上"，
> 理由是工程师一天要在里面待好几个小时。
>
> **拆出来只有"干净、留白、一种强调色"，说明没拆到位，换一家重拆。**

**3. 决定留什么、换什么。** 拿本 app 的受众、内容和使用场合逐条对照：理由同样成立的
留下，理由不成立的换掉。结果写进方向卡的"标杆与取舍"。

拆的时候分清三样东西：

| | 含义 | 处理 |
|---|---|---|
| **基线** | 用户已经期待的结构（文件管理器里列表先行、路径在顶） | 沿用，用户不用重新学 |
| **套路** | 这个品类人人都在用的默认版式 | 一轮方向里**至少一个要打破** |
| **撞脸** | 字体、配色、主视觉、图标都和某个标杆一样，只换了名字 | **任何方向都不允许** |

## 二、定调性：五个刻度

MiniApp 绝大多数是**工具型**（正则调试 / git 视图 / 计算器 / 番茄钟 / 看板）。
默认调性三句，playbook §三 有完整表述，这里不重复：

- 信息密度高，操作路径短
- 配色冷静，跟宿主主题
- 反对"营销页式"

**只有用户明确说"对外展示 / 作品集 / 灵感型"时**才进展示型调性。

要偏离默认时，用五个刻度描述，**每个刻度都写出依据**：

| 刻度 | 两端 | 在画面上看什么 |
|---|---|---|
| 能量 | 安静 ↔ 喧闹 | 饱和度、对比、元素是否碰撞 |
| 完成度 | 粗粝 ↔ 精致 | 边缘处理、颗粒噪点、对齐是否严格 |
| 密度 | 疏 ↔ 密 | 留白尺度、叠层、网格纪律 |
| 分量 | 轻 ↔ 重 | 字重、色块面积、阴影硬度 |
| 严肃度 | 活泼 ↔ 庄重 | 圆角、插画语言、动效幅度 |

**最常见的失败不是选错刻度，是没有依据的默认**：证据指向喧闹粗粝（地下现场、社区、
游戏化工具），交付的却是米色卡片 + 柔和阴影 + 大留白——设计被磨回了模型默认的
"安静高级"。反过来，给一个本该安静的产品硬加颗粒和撕纸边也是失败。

### 模糊词必须翻译

"高级、精致、克制、简洁、有质感"**不能当作设计理由**。用户或你自己说出这类词时，
先翻译成可观察的决定：

| 模糊词 | 翻译成什么 |
|---|---|
| 高级 | 先说清是哪一种高级，再决定字体对比、分隔方式、间距尺度、色相数量 |
| 精致 | 公差：字距怎么调、对齐到几像素网格、阴影最多几级、色相最多几种 |
| 克制 | 饱和度预算：强调色不超过画面 10%；动效幅度上限；色相数量上限 |
| 简洁 | 密度档位，以及**删掉什么、为什么删**。简洁是结果，不是指令 |
| 有质感 | 表面处理的具体手段：噪点 / 渐层 / 描边 / 阴影软硬，选哪个，用在哪 |

**翻译不出可观察决定的词，从理由里删掉。**

## 三、起方向：一个具体引擎，不是形容词

"做个复古的"、"做个科技感的"——这类形容词起不出方向。**每个方向从一个具体的
引擎出发**，不同方向用不同引擎：

- **一个具体场景**：有时间、地点、光线的场景（"凌晨两点的便利店"、"雨后的天台"）。
  由场景里的光线、声音、材料推出色彩、质感和动效速度。适合情绪型工具。
- **材质 × 环境**：一种材质放在一个具体环境里（"湿陶土 × 午后的工作室"）。
  由材质推出光照、深度、边缘处理和动效阻尼。
- **角色原型**：给产品一个性格（"一丝不苟的档案管理员"），让性格决定字体、色彩、动作。
- **历史媒介 × 前沿技术**：产品是 AI / 算法 / 底层基建这类无形概念时，借用有历史
  厚度的形式（单色印刷、科学测绘手稿、学术期刊、档案文献）。**借反差给无形技术
  实物分量，同时躲开"深色背景 + 紫蓝发光弥散圆晕"这个 AI 工具的集体模板。**
- **一场有真实联系的设计运动**：借它的语法，不贴它的图案。

感受词要**从这个品牌出发**，不是从行业出发。"美味、温暖、有食欲"会把每个食品
应用推向橙色；"深夜治愈、独处"才属于某一个品牌。理由只是"这行业都这么用"，就换掉。

## 四、差异检验

方向确定后、写代码前，逐条检验：

- **四项至多一项相同**：首屏骨架、字体、色彩、主视觉里，任意两个方向至多一项相同。
  否则是同一方向的变体，换个引擎重写。
- **不按明暗分方向**："一个亮、一个暗、一个暖"是头号失败。明暗是色彩身份的结果，
  不是区分方向的依据。
- **结构也要不同**：三个方向页面结构完全相同、只是颜色质感不同，还没拉开差异。
- **至少一个走到极端**：至少一个方向各项都取明确的一端，不做折中。
- **至少一个打破品类套路**（见第一节的"套路"）。打破套路 ≠ 抛弃基线：
  画廊仍然作品先行，只是排列、筛选、点开后的样子可以不同。
- **不撞脸**：和拆过的标杆并排看。字体、配色、主视觉、图标都一样只换名字，重做。
- **盲看**：遮住名字只看画面，仍能说出每个方向的不同感受。

**一个方向也要过"套路段"这一条**——只有一个方向时，问自己：这个 app 的首屏，
有没有哪个结构是这个品类的默认版式？能换掉就换。

## 五、方向卡

每个方向写一张，每项填**具体选择，不填形容词**：

| 字段 | 写到什么程度 |
|---|---|
| **北极星** | 一句能指导取舍的体验意图：用起来像在什么地方、做什么事 |
| **品类与标杆** | 是什么品类，拆的是哪一家，沿用哪几条、换掉哪几条，各自为什么 |
| **调性** | 五个刻度的取值及依据（不是"偏安静"，是"安静 7/10，因为…"） |
| **生成引擎** | 用了哪一种，具体是什么，来自这个产品的什么证据 |
| **首屏骨架** | 用户来首屏**看什么、做什么**。工具型：首屏就是工作区，第一排内容完整可见，导航+标题+筛选不超过一两行 |
| **Motif** | 一种重复的视觉元素（如"每个状态图标都坐在 20×20 圆角方块里"），全应用复用 |
| **控件语法** | 按钮、输入、选中、标签、状态、动效共用的一套形状和手感，一句话写清 |
| **记忆点** | 集中发力的一两处：在哪个时刻、什么位置、什么动作 |
| **放弃什么** | 这个方向主动不要的常见做法 |

写卡之前先在心里把方向想厚：用起来什么感觉，联想到什么表面和物件，页面怎样流转。
跳过这步，卡片只剩三十个字的空壳，页面也会是平的。

## 六、记忆点：让一处做到极致

模型做的页面常常处处及格，却没有一处让人记住。**惊艳很少来自整页都用力，
而是来自一处做到极致**——通常是一个组件的一次动作。

去哪里找：

- **用户会做的动作**：点按、拖动、切换、提交。比滚动更容易成为记忆点。
- **关键时刻**：删除、导出、第一次完成、等结果。这些时刻情绪最强。
- **边角页面**：空状态、加载、错误。没人期待，风险低，最容易出彩。
- **AI 在工作的时候**：步骤一个个亮起、日志一行行流进来。白底黑字照样成立。

怎么想：

- **让结果当场发生**：状态切换不只换一个图标，而是让被影响的东西当场变化。
- **把数字画成看得见的量**：百分比、时长、余额先问能不能画成一个量——点亮的格子、
  填满的长度。数字只是标签，量才是画面。
- **给抽象状态一种材质**：先问"这个状态如果是一个实物会是什么"，答案从产品领域里找。

## 边界：这份文件说什么，playbook 说什么

不要在这里找 token 名、动效房规、hit target 数值 —— 那些在 playbook，不要重复，
以免两处漂移。

| 归这份 | 归 playbook |
|---|---|
| 品类与标杆 | 43 个 `--hamuna-*` token 全表 |
| 调性五刻度 | 反 AI 味清单 |
| 生成引擎 | 配色三步序与色板表 |
| 差异检验 | 动效房规与降级 |
| 方向卡 | 排版字号、hit target、modality |
| 记忆点 | `meta.json::appearance` 声明格式 |

**冲突时以 playbook 为准** —— 它是 `npm run lint` 里那条审计命令的依据，
这份文件不是。方向可以另类，token 契约不可以。
