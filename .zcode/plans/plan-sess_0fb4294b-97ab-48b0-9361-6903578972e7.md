## 改动

### 1. 新增共享服务 `src/renderer/config/services/mcpEnableService.ts`

放在 `config/services/`，符合本仓库「无 React 的纯服务 + 调用方注入副作用」惯例（同 `persistInputOption.ts`）。

```ts
export type McpEnableOutcome =
  | { ok: true; playwrightArgsInitialized: boolean }
  | { ok: false; kind: 'missing-config'; missingKeys: string[] }
  | { ok: false; kind: 'runtime-missing'; runtimeName?; downloadUrl?; command? }
  | { ok: false; kind: 'failed'; message: string };

/** 哪些 requiresConfig 键还没填 */
export async function findMissingMcpConfigKeys(server): Promise<string[]>

/** 唯一启用路径：配置校验 → POST /api/mcp/enable → 错误分类 */
export async function enableMcpServer(server, opts?): Promise<McpEnableOutcome>
```

要点：
- **配置缺失时直接短路，不发请求** —— 省掉一次无意义的 npx 握手
- 服务返回结构化结果，**toast / 弹窗由调用方决定**，服务不认识任何 UI
- 顺带把 Playwright 首次启用的默认 args 写入收进服务（`playwrightArgsInitialized` 标志让调用方决定是否刷新列表）
- 复用 `apiPostJson`，顺带消掉 Chat 用 `apiPost` / Settings 用 `apiPostJson` 的不一致

## 一处取舍，需要你确认

我原本问的是「Chat 补齐下载引导**弹窗**」，但实际做下来：**Chat 侧只补 toast，不补弹窗**。

原因是 Settings 的 `handleEditBuiltinMcp` 有约 200 行按服务器分支的专用弹窗（edge-tts / gemini-image / playwright 各一套），而 `runtimeDialog` 又耦合了 Settings 的 providers/apiKeys 状态。把它搬进 Chat 会显著放大改动面，且与「共享启用逻辑」这个目标不成比例。

所以：**判定逻辑完全共享**（同一个服务做出同一个判定），只是渲染方式不同 —— Settings 弹窗、Chat toast（文案带下载链接并指向设置页）。如果你要 Chat 也出真弹窗，我需要再抽一个共享 `McpRuntimeMissingDialog` 组件，那是独立的一块工作，可以后续单独做。
